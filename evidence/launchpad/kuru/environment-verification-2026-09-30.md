# Monad Testnet Kuru environment verification — 2026-09-30

**Classification:** KURU-B1-ENVIRONMENT `PASS` for the block-pinned, read-only identity check. `KURU_TARGET_FROZEN` remains `BLOCKED`. No ADR is accepted by this record.

The [machine-readable manifest](environment-manifest-2026-09-30.json) captures block `66752717` (2026-09-29 18:00:05 UTC), chain ID `10143`, the official-testnet Router and USDC addresses, Router's MarginAccount and implementation getters, deployed code lengths, and code hashes. The public [Kuru contracts](https://github.com/Kuru-Labs/Kuru-contracts-dex-public/tree/2060bb2736080c175d80d568bfdb6226bb5abd04) and [SDK](https://github.com/Kuru-Labs/kuru-sdk/tree/636509c2eafd63479d3f399703354e0d09f51e18) heads matched those pins at retrieval. [Kuru's address page](https://docs.kuru.io/contracts/Contract-addresses) listed the same testnet Router and USDC. The SDK package version at its pinned commit was `0.0.97`.

Router's pinned source provides `deployProxy`, `computeAddress`, `computeVaultAddress` and the `verifiedMarket` state getter. The four selectors in the manifest were independently derived with `cast sig`. Runtime code exists at Router, MarginAccount, OrderBook implementation, vault implementation and USDC; Router getter values matched the manifest. The Router is an EIP-1967 proxy, so the manifest additionally records its implementation address and runtime hash. The implementation hashes matched the 2026-09-29 snapshot, but that historical match alone is not a future drift guarantee.

Reproduction uses `cast chain-id`, `cast block-number`, `cast call` for Router getters and `decimals()`, `cast storage` at the EIP-1967 implementation slot, and `cast code --block 66752717` for each address. This RPC returned `Method not found` for `cast codehash` (which uses an unavailable RPC method), so hashes were computed as `cast keccak <runtime-bytecode-from-cast-code>`; no hash was inferred from an explorer. The same commands must be rerun against a fresh block immediately before fork/live execution and again within the eventual onchain phase-2 transaction.

This is only B1. Quote behavior and issuer trust (B2), parameter policy (B3), seed acceptance (B4), fork deployment/seed, custody, retry, gas and live usability are separate gates. The present snapshot does not justify `KURU_TARGET_FROZEN` or production executor work.

## Quote identity discrepancy found during B2 inspection

Kuru's [official testnet address page](https://docs.kuru.io/contracts/Contract-addresses) labels `0x3bA3d39AFcf8bb994f7964B3e0171Ea2Ba361570` as USDC. Circle's [official USDC address page](https://developers.circle.com/stablecoins/usdc-contract-addresses) instead lists `0x534b2f3A21130d7a60830c2Df862319e593943A3` for Monad Testnet. At the snapshot block both had code and six decimals, but their runtime hashes and `name()` values differed. The Circle-listed token exposed owner, pauser, blacklister and master-minter roles and was not paused; the Kuru-listed token did not return those Circle-style role getters in the read-only calls. Neither Actor A nor Actor B held either token at inspection. This is `RECORDED_CONTRADICTION`, not proof that either token is unsafe or that Kuru cannot list the Circle token. B2 and ADR-011 must select an exact address and qualify its transfer/allowance/Kuru behavior; `USDC` symbol matching is insufficient.
